# mach-vk

Mach declarations for [Vulkan](https://registry.khronos.org/vulkan/): the raw
Vulkan C ABI expressed in pure Mach — types, handles, enums, structs, and a
dynamically loaded command table — generated from the Khronos `vk.xml` registry.
Project id is `vk`, so consumers reach everything as `vk.*`.

Same philosophy as [mach-gl](https://github.com/briar-systems/mach-gl): no
wrapped library, no C in the tree, nothing linked at the binding level. Vulkan
is declared, not vendored; every command is resolved at runtime through the
standard loader chain a consumer drives.

> **Status: core and WSI generated.** `tools/gen.py` emits the full core Vulkan
> surface (1.0–1.3) plus a curated extension allowlist — surface, swapchain, the
> xlib/wayland/win32/metal platform surfaces, and debug_utils — from a pinned
> `vk.xml`; the committed `src/*.mach` are its output. Video and Vulkan SC are
> not generated. See [`tools/README.md`](tools/README.md).

```mach
use vk;

# gipa is the platform's vkGetInstanceProcAddr — obtained from the Vulkan loader
# (libvulkan.so.1 / vulkan-1.dll) or a windowing layer that exposes it.
fun example(gipa: vk.GetInstanceProcAddr) {
    vk.load_global(gipa);

    var api: u32 = 0;
    vk.vkEnumerateInstanceVersion(?api);
    # ... create an instance, vk.load_instance(gipa, instance), select a device,
    #     vk.load_device(gdpa, device), then record and submit work.
}
```

Consuming projects vendor the declarations as a normal Mach dependency. There is
no system link requirement: `mach-vk` declares no `libs` and forces none on
consumers. The consumer owns the loader — dynamic-linking `libvulkan`, `dlopen`,
or a windowing library's proc-address hook are all equally valid.

```toml
[deps.mach-vk]
git = "https://github.com/briar-systems/mach-vk"
ref = "branch/main"
```

## Goals

- Coverage of the core Vulkan API surface (1.0–1.3) plus the WSI and debugging
  extensions a renderer actually needs, generated mechanically from the pinned
  Khronos registry (`tools/vk.xml`).
- Zero-cost: raw declarations over a table of loaded function pointers; no
  allocation, no registries, no hidden state beyond the pointers the loaders
  fill.
- C-faithful types and C names — any Vulkan reference maps directly. Opaque
  handles are `ptr`, transparent structs are `rec`s with identical layout.
- Loader-agnostic: anything that can produce a `vkGetInstanceProcAddr` drives
  the whole chain.

## Non-goals

- A safety layer or high-level renderer. mach-vk is raw declarations; validation,
  RAII, and an ergonomic API belong in the engine's RHI, not the binding.
- Window-surface creation beyond what pairs with a windowing library. Surface
  creation is a sibling concern owned by the windowing layer — the Vulkan-WSI
  interop point is `glfwCreateWindowSurface` in
  [mach-glfw](https://github.com/briar-systems/mach-glfw), not mach-vk.
- Shader compilation — see [Shaders](#shaders).

## Loading

Vulkan commands cannot be linked; an implementation exposes them only through
the loader chain, and mach-vk mirrors that chain directly:

1. The consumer provides the bootstrap `vkGetInstanceProcAddr` (`vk.load_global`
   passes it a nil instance to resolve the instanceless global commands —
   `vkCreateInstance`, `vkEnumerateInstance*`).
2. After `vkCreateInstance`, `vk.load_instance(gipa, instance)` resolves the
   instance-level commands.
3. After `vkCreateDevice`, `vk.load_device(gdpa, device)` narrows the
   device-level commands through `vkGetDeviceProcAddr`, skipping the instance
   dispatch trampoline for hot paths.

A command the running implementation does not export stays `nil`; calling one is
the same contract as in C. The raw table is reachable as `vk.c.vkCreateInstance`
for anyone who wants C names.

## Architecture

Everything between the loaders and the surface is generated by `tools/gen.py`
from the vendored registry; CI's Generation-drift job regenerates and diffs, so
a build fails if the committed sources drift from the pinned `vk.xml`.

```
src/
  types.mach    opaque handle aliases (generated); a leaf layer, imports nothing
  enums.mach    enumerant, bitmask, and extension-name constants (generated)
  structs.mach  struct and union records with C-identical layout, plus the PFN_*
                callback aliases (generated)
  c.mach        raw command table + loaders (generated): one pub var function
                pointer per command, plus load_global / load_instance /
                load_device
  vk.mach       library surface (generated): re-exports every symbol under vk.*,
                keeping vk.c reachable for C names
tools/
  gen.py        registry generator; emits all generated sources
  vk.xml        pinned Khronos registry snapshot
test/
  smoke/        a separate consuming project that links a real Vulkan loader and
                drives the binding against a live ICD; see Tests
```

`[project].module = "vk.mach"` makes a bare `use vk;` resolve to the surface, and
the project is a `[lib.vk]` artifact entered through it. The surface carries
`use std.runtime;` so a library `mach test` links a runnable binary.

See [`tools/README.md`](tools/README.md) for the generation approach and the
`vk.xml` pin.

## Shaders

Vulkan consumes [SPIR-V](https://registry.khronos.org/SPIR-V/), not source. Until
the Mach compiler grows its planned SPIR-V target, shaders are compiled offline
(e.g. `glslc` from the Vulkan SDK) as an asset-pipeline step. That is a temporary
toolchain dependency of a project's build, **not** a binding concern: mach-vk
declares the API that consumes SPIR-V modules and nothing about producing them.

## Platforms

The declarations are platform-agnostic — the Vulkan ABI is identical across
operating systems, so one generated surface serves all of them. What varies is
the loader/ICD story, which the consumer owns: the OS's Vulkan loader
(`libvulkan.so.1`, `libvulkan.1.dylib` via MoltenVK, `vulkan-1.dll`) resolves
`vkGetInstanceProcAddr`, and mach-vk chains from there.

The Mach compiler currently targets the `x86_64`, `aarch64`, and `riscv64` ISAs
across `linux`, `darwin`, and `windows`; `mach.toml` declares the three
`x86_64` triples that are exercised today, and the bindings compile for any
target the toolchain supports.

## Tests

`test` blocks are display-free and need no Vulkan loader: they resolve the
command table with stub loaders (a nil loader must leave the table nil and
report zero; a counting loader must resolve every command) and call through the
table into a Mach-implemented fake, which pins the loaded-pointer call ABI
without a Vulkan implementation present.

Paths that need a live loader and a real ICD live in `test/smoke/`, which is a
**separate project** that consumes mach-vk by path rather than a target inside
this manifest. That separation is load-bearing, not tidiness: `mach test` links
the union of every artifact's link entries across a project, so a single
Vulkan-linking artifact in this manifest would pull `libvulkan` into the
binding's own test binary and break the guarantee above. Keeping the smoke test
one project out is what lets `mach test .` here stay link-free.

`test/smoke` doubles as the reference bootstrap: it shows the whole chain a
consumer owns — declaring `vkGetInstanceProcAddr`, linking the platform loader
through its own `[link.vulkan-*]` entries, and driving `load_global` →
`load_instance` → `load_device` to a live device and queue.
